# 모바일·웹 공통 User Flow 및 UI 계약

이 문서는 현재 확정된 모바일 S01~S07 화면을 기준으로 모바일 앱과 웹이 같은 정보 구조, 문구, 상태, 버튼 우선순위와 화면 이동을 구현하기 위한 기준이다.

구현의 최종 기준은 다음 순서로 판단한다.

1. 이 문서의 화면 순서와 문구
2. 각 화면의 `*.types.ts` View props 계약
3. 모바일 기본 View인 `*.tsx`의 상태별 표시 방식
4. `apps/mobile/src/theme/tokens.ts`의 디자인 토큰

웹 담당자는 Screen과 service를 다시 만들지 않고 동일한 Screen이 전달하는 props로 `*.web.tsx` View만 구현한다. 웹에서도 데스크톱용으로 정보 순서나 CTA 우선순위를 임의로 바꾸지 않는다.

## 2. 표기 규칙

- `UI`: View에 고정된 문구와 표시 요소
- `USER`: 사용자가 입력하거나 수정하는 데이터
- `AI`: 음성 처리 또는 사건 분석 결과
- `API`: 서버·기기 service에서 받은 데이터
- `STATE`: 대기·처리 중·오류·완료 상태에 따라 달라지는 요소

## 3. 전체 화면 공통 UI 규칙

### 3.1 헤더

S02~S06은 동일한 `FlowHeader` 구조를 사용한다.

```text
[뒤로가기]          [중앙 화면 제목]          [빈 영역]
```

- 헤더 높이는 최소 `52`다.
- 좌우 영역은 각각 `48` 너비를 확보해 제목을 화면 중앙에 고정한다.
- 좌측에는 파란색 뒤로가기 화살표를 표시한다.
- **우측 상단에 `3/6`, `4/6`, `5/6`, `6/6` 같은 단계 숫자를 표시하지 않는다.**
- 모바일과 웹 모두 우측 영역을 다른 정보나 버튼으로 채우지 않는다.
- S01은 별도 헤더 없이 자체 홈 구성을 사용한다.

S03·S04·S05의 얇은 가로 ProgressBar와 S04 본문의 질문 순서 `1 / N`은 헤더 단계 숫자가 아니다. 현재 화면 내부 기능으로 유지한다.

S07은 하단 탭에서 진입하는 서류 허브이므로 화면명 `서류`를 좌측 뒤로가기 버튼 옆에 표시한다. S07에도 우측 단계 숫자나 별도 액션을 표시하지 않는다.

### 3.2 하단 내비게이션

S07 와이어프레임에서 확인된 하단 내비게이션은 `사건`, `가이드`, `서류` 3개 탭으로 구성한다.

- 각 탭은 아이콘과 한글 label을 함께 표시한다.
- 현재 화면인 `서류` 탭은 파란색 채움 배경과 흰색 아이콘·글씨로 활성 상태를 명확히 표시한다.
- 비활성 탭은 흰색 배경에 회색 아이콘·글씨를 사용한다.
- 하단 safe area를 포함하고 본문과 겹치지 않도록 한다.
- 탭의 실제 연결 화면은 해당 화면 명세가 확정될 때 route를 최종 확정한다.

### 3.4 간격·모서리·버튼

- 기본 간격 단위: `4`, `8`, `16`, `24`, `32`
- 기본 콘텐츠 좌우 여백: `16`
- 카드 radius: `12~16`
- 입력창과 주요 버튼 최소 높이: `52`
- primary 버튼: 파란 배경, 흰색 굵은 글씨
- secondary 버튼: 연한 파란 배경, 파란 글씨
- outline 버튼: 흰색 배경, 회색 border, 짙은 글씨
- 처리 중 버튼은 spinner를 표시하고 중복 클릭을 막는다.
- 오류는 연한 빨간 배경과 빨간 글씨로 입력 또는 관련 CTA 가까이에 표시한다.

### 3.5 레이아웃과 반응형

- 모든 화면은 세로 스크롤이 가능해야 한다.
- 키보드가 열려도 현재 입력창과 하단 CTA가 가려지지 않아야 한다.
- 고정 footer가 있는 화면은 본문과 footer가 겹치지 않아야 한다.
- 웹은 모바일과 동일한 세로 정보 순서를 유지하고 콘텐츠 최대 너비를 약 `480px`로 제한해 중앙 정렬한다.
- 와이드 화면이라는 이유로 카드 순서나 CTA를 좌우 다단 레이아웃으로 재설계하지 않는다.
- 모바일에서 2열인 버튼·정보 행은 웹의 동일 폭 콘텐츠에서도 2열을 유지한다.
- 접근성 터치·클릭 영역은 최소 `44×44`를 확보한다.

### 3.6 View 구현 경계

- Screen: Router, Context, API·device service, 검증, 비동기 상태 관리
- View: 전달받은 props 표시와 사용자 이벤트 전달
- 앱 View: `SomethingView.tsx`
- 웹 View: `SomethingView.web.tsx`
- 앱·웹 View는 같은 `SomethingView.types.ts`를 사용한다.
- View에서 Context, Router, Expo Audio, Expo Location, API client를 직접 호출하지 않는다.

# S02. 음성·텍스트 사건 입력

## View 계약

```text
apps/mobile/src/features/case/views/VoiceInputView.types.ts
```

## 확정 화면 순서 — 음성 모드

1. 공통 헤더
   - 중앙 제목 `분실·도난 신고`
   - 우측 단계 숫자 없음
2. 왼쪽 정렬 제목 `무슨 일이 있었는지 알려주세요`
3. 설명 `사건의 경위를 말씀해주시면 자동으로 신고서 초안을 작성합니다.`
4. 화면 중심의 큰 원형 마이크
5. 마이크 바로 아래 녹음 상태와 `00:00` 형식 시간
6. 연한 파란 음성 인식 문장 카드
7. 상태에 따른 전체 너비 primary CTA
8. 동일 너비 2열 버튼 `다시 녹음`, `텍스트 입력`
9. 2열 compact 정보 `현재 위치`, `현지 시간`
10. 작은 하단 안내 `네트워크가 불안정하면 텍스트로 계속 입력할 수 있습니다.`

## 마이크와 리플

- 중앙 마이크 버튼은 약 `92×92`, 전체 애니메이션 영역은 약 `148×148`이다.
- idle 상태에서는 파란 고정 외곽선을 표시한다.
- 녹음 중에는 마이크 뒤의 원 2개가 순차적으로 확대되며 투명해지는 리플을 반복한다.
- 리플은 녹음 중에만 실행하고 정지·처리·오류 상태에서 정리한다.
- 동작 줄이기 설정에서는 반복 animation 대신 고정 halo를 표시한다.
- 웹은 CSS keyframes 또는 Web Animation으로 같은 scale·opacity 흐름을 구현하고 `prefers-reduced-motion`을 적용한다.

## 상태별 UI

| 상태 | 마이크 아래 문구 | 주요 CTA | 입력 제한 |
|---|---|---|---|
| idle, 문장 없음 | `눌러서 녹음을 시작하세요` | 마이크로 녹음 시작 | 텍스트 입력 가능 |
| 권한 확인 중 | `마이크 권한 확인 중` | loading | 중복 입력 차단 |
| 녹음 중 | 빨간 점 + `녹음 중...` | `녹음 중지` | 텍스트 전환 시 녹음 정리 |
| 녹음 정리 중 | `녹음을 정리하고 있어요` | loading | 중복 입력 차단 |
| 음성 처리 중 | `음성을 텍스트로 변환하고 있어요` | `음성 처리 중` | 중복 입력 차단 |
| 인식 완료 | `음성 인식 완료` | `입력 내용 확인하기 →` | S03 이동 가능 |
| 오류 | `다시 시도해 주세요`와 오류 카드 | 다시 녹음 또는 설정 열기 | 텍스트 fallback 유지 |

음성 문장은 녹음 종료 후 service가 텍스트로 변환한다. 실시간 변환으로 오해하게 만드는 문구를 사용하지 않는다.

## 텍스트 모드

- 사용자가 `텍스트 입력`을 누르면 사건 내용 multiline 입력창을 표시한다.
- 하단에 `마이크로 입력`, `입력 내용 확인` 2열 버튼을 표시한다.
- 마이크로 돌아갈 때 입력한 문장은 draft에 유지한다.
- 공백을 제거한 문장이 없으면 S03 이동을 막는다.

## 위치·시간

- 기본 상태는 2열 compact 정보 행이다.
- 위치 또는 시간을 누르면 `장소와 시간 수정` 카드가 펼쳐진다.
- 펼친 카드에는 `현재 위치 사용`, 장소 입력, 시간 입력을 표시한다.
- 현재 위치는 Expo Location 경계를 통해 조회하고 표시 문자열과 좌표를 구분해 저장한다.
- 위치 권한 거부 또는 조회 실패 시 편집 카드를 자동으로 열고 직접 입력을 제공한다.
- 위치 조회 성공 시 편집 카드를 닫고 compact 위치를 갱신한다.

# S03. 입력 내용 확인

## 확정 화면 순서

1. 공통 헤더: 중앙 제목 `내용 확인`, 우측 단계 숫자 없음
2. 얇은 가로 ProgressBar
3. 제목 `말씀해주신 내용이 맞나요?`
4. `사건 내용` 카드와 `내용 수정` 버튼
5. `사건 발생 장소` 카드와 `장소 수정` 버튼
6. `사건 발생 시간` 카드와 `시간 수정` 버튼

   - 예상 신고서 유형
   - 추가 질문 준비 안내

   - 현재 질문 한 개
   - multiline 답변 입력
8. 처리 중 또는 오류 상태 카드
9. 고정 footer
   - 첫 질문이 아니면 `이전 질문`
   - 중간 질문은 `다음 질문`
   - 마지막 질문은 `답변 완료하고 분석하기`

헤더 우측 단계 숫자는 없지만 질문 본문의 `1 / N`은 사용자가 현재 질문 위치를 파악하기 위해 유지한다.

## 상태와 이동

| 동작·상태 | 결과 |
|---|---|
| 답변 입력 | Context에 즉시 저장 |
| 이전 질문 | 기존 답변을 유지하고 이전 질문 표시 |
| 빈 답변으로 다음·완료 | 이동 차단, 필수 답변 오류 표시 |
| 마지막 분석 중 | 입력·버튼 비활성화, 중복 요청 차단 |
| 분석 실패 | 답변 유지, 오류와 `다시 분석하기` 표시 |
| 분석 성공 | 사건 카드 요약을 draft에 적용하고 S05 이동 |
| 질문 없음 | 오류 안내와 `내용 확인으로 돌아가기` 표시 |
| 뒤로가기 | S03 이동 |

## 데이터 표시 규칙

- 사건번호, 신고 상태, 진행률, 문서 생성 여부와 증빙 자료 정보는 현재 사건을 기준으로 Screen에서 전달한다.
- 사건번호 형식은 S06과 동일한 formatter를 사용한다. 와이어프레임의 `JP2024-00129`는 예시 데이터이며 화면마다 서로 다른 표기 규칙을 만들지 않는다.

- 상태 badge 문구는 API 상태를 사용자용 문구로 변환한 값이다. 현재 와이어프레임의 완료 상태 문구는 `신고 완료`다.
- 생성되지 않은 문서 또는 존재하지 않는 증빙 자료는 빈 카드로 위장하지 않고 `준비 중`, `아직 등록된 자료가 없습니다`처럼 상태를 명시한다.
- 긴 제목과 설명은 카드의 `보기`·`공유` 버튼을 밀어내지 않도록 본문 영역에서 줄바꿈한다.

## 4. 웹 구현 완료 기준

- S01~S07의 정보 순서와 고정 문구가 이 문서와 같다.
- S02~S06 헤더 우측에 단계 숫자가 없다.
- 앱과 웹이 동일한 `*.types.ts` props를 사용한다.
- 앱과 웹에서 primary·secondary·outline CTA 우선순위가 같다.

- 웹의 키보드 Tab 이동과 focus 표시가 가능하다.
- `prefers-reduced-motion`에서 S02 리플 반복을 중지한다.
- 모바일 폭에서 앱 실기기 화면과 같은 순서·간격·줄바꿈을 유지한다.
- 데스크톱에서도 콘텐츠만 중앙 정렬하고 별도의 데스크톱 정보 구조로 바꾸지 않는다.
- S07의 카드 순서, 진행률, 상태 badge와 하단 탭 구성을 모바일과 동일하게 유지한다.
