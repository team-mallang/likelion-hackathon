# 모바일·웹 공통 User Flow 및 UI 계약

이 문서는 현재 확정된 모바일 S01~S07, S09, S11, S14, S19 및 S20 화면을 기준으로 모바일 앱과 웹이 같은 정보 구조, 문구, 상태, 버튼 우선순위와 화면 이동을 구현하기 위한 기준이다.

구현의 최종 기준은 다음 순서로 판단한다.

1. 이 문서의 화면 순서와 문구
2. 각 화면의 `*.types.ts` View props 계약
3. 모바일 기본 View인 `*.tsx`의 상태별 표시 방식
4. `apps/mobile/src/theme/tokens.ts`의 디자인 토큰

웹 담당자는 Screen과 service를 다시 만들지 않고 동일한 Screen이 전달하는 props로 `*.web.tsx` View만 구현한다. 웹에서도 데스크톱용으로 정보 순서나 CTA 우선순위를 임의로 바꾸지 않는다.

- S19는 `/api/cases/auth` 인증 service와 S07 연결까지 구현되었다. 실제 API 주소 설정과 실기기 QA가 남아 있다.
- S20은 이전에 불러온 사건의 읽기 전용 사건카드 상세와 `/api/cases/[id]` 조회 service, S07 연결까지 구현되었다. 추출·공유 기능은 아직 시작하지 않는다.
- S11은 가이드 DB와 사건 카드 기반의 추천 구조, 모바일 도메인 타입·View props·가이드 카드 UI·mock service·웹/접근성 대응까지 구현되었다. 실제 API 연동과 실기기 QA가 남아 있다.
- S11·S19·S20의 모바일 타입 검사와 diff 정적 검증을 통과했다. 실기기·API 환경 QA는 아직 진행하지 않았다.
- S14는 마이크 시작 전 여행자 음성 처리 안내와 경찰관 고지 확인을 각각 받아야 하며, 두 확인 전에는 통역을 시작할 수 없다. 통역 오류는 원격 오류 본문 대신 안전한 안내 문구만 표시한다.
- S09·S14는 공통 View를 최대 480px 폭으로 웹에도 표시한다. S09 언어 전환과 S14 final 번역 완료는 스크린 리더에 상태를 알리고, 웹 S14는 native Agora 모듈 없이 mock 통역으로 안전하게 동작한다.
- S09 mock 신고서 service와 S14 대화 reducer의 자동 테스트 6개를 추가했다. 언어 쌍·필수 정보·source revision·이벤트 순서·오류 메시지 비보존을 검증하며, 실제 API·Agora는 통합 환경이 준비된 뒤 검증한다.

## 3. 전체 화면 공통 UI 규칙

### 3.1 헤더

S02~S06은 동일한 `FlowHeader` 구조를 사용한다.

```text
[뒤로가기]          [중앙 화면 제목]          [빈 영역]
```

- 헤더 높이는 최소 `52`다.
- 좌우 영역은 각각 `48` 너비를 확보해 제목을 화면 중앙에 고정한다.
- 좌측에는 파란색 뒤로가기 화살표를 표시한다.
- **우측 상단에 `3/6`, `4/6`, `5/6`, `6/6` 같은 단계 숫자를 표시하지 않는다.**
- 모바일과 웹 모두 우측 영역을 다른 정보나 버튼으로 채우지 않는다.
- S01은 별도 헤더 없이 자체 홈 구성을 사용한다.

S03·S04·S05의 얇은 가로 ProgressBar와 S04 본문의 질문 순서 `1 / N`은 헤더 단계 숫자가 아니다. 현재 화면 내부 기능으로 유지한다.

S07은 하단 탭에서 진입하는 서류 허브이므로 화면명 `서류`를 좌측 뒤로가기 버튼 옆에 표시한다. S07에도 우측 단계 숫자나 별도 액션을 표시하지 않는다.

S19는 S02~S06의 신규 사건 작성 흐름이 아니라 이전 사건을 불러오는 별도 흐름이다. 제공된 화면을 기준으로 중앙 제목 `분실·도난 신고`와 우측 단계 표시 `3/6`을 함께 사용한다. 이 예외는 S02~S06의 우측 빈 영역 규칙을 변경하지 않는다.

S11도 사건 작성 완료 후의 행동 가이드 흐름으로 제공된 화면 기준 중앙 제목 `분실·도난 신고`와 우측 `3/6` 표시를 사용한다. 이 숫자가 S11의 실제 진행 단계를 뜻하는지는 구현 전에 확정한다. 확정 전에는 S02~S06의 `FlowHeader` 규칙으로 일반화하지 않는다.

### 3.2 하단 내비게이션

S07, S11, S19와 S20에서 확인된 하단 내비게이션은 `사건`, `가이드`, `서류` 3개 탭으로 구성한다.

- 각 탭은 아이콘과 한글 label을 함께 표시한다.
- 현재 화면인 `서류` 탭은 파란색 채움 배경과 흰색 아이콘·글씨로 활성 상태를 명확히 표시한다.
- 비활성 탭은 흰색 배경에 회색 아이콘·글씨를 사용한다.
- 하단 safe area를 포함하고 본문과 겹치지 않도록 한다.
- 탭의 실제 연결 화면은 해당 화면 명세가 확정될 때 route를 최종 확정한다.
- S19 제공 화면도 `서류` 탭을 활성 상태로 표시한다. S19에서 이 활성 상태가 의미하는 정보 구조와 각 탭의 목적 route는 구현 전에 기획 확인이 필요하다.
- S11에서는 `가이드` 탭을 활성 상태로 표시한다.
- S20에서는 `서류` 탭을 활성 상태로 표시한다. 제공 이미지의 영문 label은 예시이므로 실제 label 언어는 공통 정책으로 통일한다.

### 3.4 간격·모서리·버튼

- 기본 간격 단위: `4`, `8`, `16`, `24`, `32`
- 기본 콘텐츠 좌우 여백: `16`
- 카드 radius: `12~16`
- 입력창과 주요 버튼 최소 높이: `52`
- primary 버튼: 파란 배경, 흰색 굵은 글씨
- secondary 버튼: 연한 파란 배경, 파란 글씨
- outline 버튼: 흰색 배경, 회색 border, 짙은 글씨
- 처리 중 버튼은 spinner를 표시하고 중복 클릭을 막는다.
- 오류는 연한 빨간 배경과 빨간 글씨로 입력 또는 관련 CTA 가까이에 표시한다.

### 3.5 레이아웃과 반응형

- 모든 화면은 세로 스크롤이 가능해야 한다.
- 키보드가 열려도 현재 입력창과 하단 CTA가 가려지지 않아야 한다.
- 고정 footer가 있는 화면은 본문과 footer가 겹치지 않아야 한다.
- 웹은 모바일과 동일한 세로 정보 순서를 유지하고 콘텐츠 최대 너비를 약 `480px`로 제한해 중앙 정렬한다.
- 와이드 화면이라는 이유로 카드 순서나 CTA를 좌우 다단 레이아웃으로 재설계하지 않는다.
- 모바일에서 2열인 버튼·정보 행은 웹의 동일 폭 콘텐츠에서도 2열을 유지한다.
- 접근성 터치·클릭 영역은 최소 `44×44`를 확보한다.

### 3.6 View 구현 경계

- Screen: Router, Context, API·device service, 검증, 비동기 상태 관리
- View: 전달받은 props 표시와 사용자 이벤트 전달
- 앱 View: `SomethingView.tsx`
- 웹 View: `SomethingView.web.tsx`
- 앱·웹 View는 같은 `SomethingView.types.ts`를 사용한다.
- View에서 Context, Router, Expo Audio, Expo Location, API client를 직접 호출하지 않는다.

# S02. 음성·텍스트 사건 입력

## View 계약

```text
apps/mobile/src/features/case/views/VoiceInputView.types.ts
```

## 확정 화면 순서 — 음성 모드

1. 공통 헤더
   - 중앙 제목 `분실·도난 신고`
   - 우측 단계 숫자 없음
2. 왼쪽 정렬 제목 `무슨 일이 있었는지 알려주세요`
3. 설명 `사건의 경위를 말씀해주시면 자동으로 신고서 초안을 작성합니다.`
4. 화면 중심의 큰 원형 마이크
5. 마이크 바로 아래 녹음 상태와 `00:00` 형식 시간
6. 연한 파란 음성 인식 문장 카드
7. 상태에 따른 전체 너비 primary CTA
8. 동일 너비 2열 버튼 `다시 녹음`, `텍스트 입력`
9. 2열 compact 정보 `현재 위치`, `현지 시간`
10. 작은 하단 안내 `네트워크가 불안정하면 텍스트로 계속 입력할 수 있습니다.`

## 마이크와 리플

- 중앙 마이크 버튼은 약 `92×92`, 전체 애니메이션 영역은 약 `148×148`이다.
- idle 상태에서는 파란 고정 외곽선을 표시한다.
- 녹음 중에는 마이크 뒤의 원 2개가 순차적으로 확대되며 투명해지는 리플을 반복한다.
- 리플은 녹음 중에만 실행하고 정지·처리·오류 상태에서 정리한다.
- 동작 줄이기 설정에서는 반복 animation 대신 고정 halo를 표시한다.
- 웹은 CSS keyframes 또는 Web Animation으로 같은 scale·opacity 흐름을 구현하고 `prefers-reduced-motion`을 적용한다.

## 상태별 UI

| 상태 | 마이크 아래 문구 | 주요 CTA | 입력 제한 |

| 권한 확인 중 | `마이크 권한 확인 중` | loading | 중복 입력 차단 |

| 녹음 정리 중 | `녹음을 정리하고 있어요` | loading | 중복 입력 차단 |
| 음성 처리 중 | `음성을 텍스트로 변환하고 있어요` | `음성 처리 중` | 중복 입력 차단 |
| 인식 완료 | `음성 인식 완료` | `입력 내용 확인하기 →` | S03 이동 가능 |
| 오류 | `다시 시도해 주세요`와 오류 카드 | 다시 녹음 또는 설정 열기 | 텍스트 fallback 유지 |

음성 문장은 녹음 종료 후 service가 텍스트로 변환한다. 실시간 변환으로 오해하게 만드는 문구를 사용하지 않는다.

## 텍스트 모드

- 사용자가 `텍스트 입력`을 누르면 사건 내용 multiline 입력창을 표시한다.
- 하단에 `마이크로 입력`, `입력 내용 확인` 2열 버튼을 표시한다.
- 마이크로 돌아갈 때 입력한 문장은 draft에 유지한다.
- 공백을 제거한 문장이 없으면 S03 이동을 막는다.

## 위치·시간

- 기본 상태는 2열 compact 정보 행이다.
- 위치 또는 시간을 누르면 `장소와 시간 수정` 카드가 펼쳐진다.
- 펼친 카드에는 `현재 위치 사용`, 장소 입력, 시간 입력을 표시한다.
- 현재 위치는 Expo Location 경계를 통해 조회하고 표시 문자열과 좌표를 구분해 저장한다.
- 위치 권한 거부 또는 조회 실패 시 편집 카드를 자동으로 열고 직접 입력을 제공한다.
- 위치 조회 성공 시 편집 카드를 닫고 compact 위치를 갱신한다.

| 동작 | 조건 | 결과 |
|---|---|---|
| 뒤로가기 | 항상 | 녹음 resource 정리 후 S01 |
| 마이크 | idle | 권한 확인 후 녹음 시작 |
| 녹음 중지 | 녹음 중 | 녹음 종료 후 음성 처리, S02 유지 |

# S09. 경위서 초안

## 정의 상태

- 이 절의 화면 구성과 고정 문구는 제공된 S09 와이어프레임을 기준으로 한다.
- S09는 사용자가 입력하고 확인한 사건 정보를 바탕으로 AI가 작성한 일본 경찰 제출용 일본어 `被害届` 초안을 확인하는 화면이다.
- 이 화면의 문서는 제출이 완료된 정식 신고서가 아니다. 사용자가 내용을 검토·수정한 뒤 저장하거나 공유하기 위한 초안이다.
- `/case/report` route, Screen, 모바일·웹 View, mock 생성·조회·재생성 상태와 S07 진입 연결이 구현되었다. 언어 switch는 현재 원본·확인본 상태를 스크린 리더에 알리고, service 오류 원문 대신 안전한 사용자 안내를 표시한다. S09 mock service의 언어 쌍·필수 정보·source revision 규칙은 자동 테스트로 검증한다. 실제 API, 내용 수정과 저장·공유 service는 아직 구현하지 않는다.
- 신고인 정보와 사건 상세에는 개인정보와 민감한 사건 정보가 포함되므로 화면 표시, 로그, 저장과 공유에서 보안 정책을 적용한다.

## View 계약

구현 시 앱과 웹이 하나의 `*.types.ts` View props 계약을 공유한다. 파일 경로와 컴포넌트 이름은 기존 documents feature 구조를 확인한 뒤 확정한다.

필수 props 범위는 다음과 같다.

- 일본어 신고서 초안 데이터와 초안 생성·조회 상태
- 한국어 확인 모드 여부와 토글 이벤트
- 신고인 정보, 사건 개요, 피해 물품 목록, 피해 상황 상세
- 수정 가능 여부와 `내용 수정` 이벤트
- 저장·공유 가능 여부, 처리 중 상태와 `저장/공유` 이벤트
- 뒤로가기와 하단 탭 이벤트
- 조회·번역·저장·공유 오류

## 데이터 생성·표시 규칙

- 신고서 초안은 S05에서 사용자가 최종 확인한 사건 카드와 신고인 정보를 단일 원본으로 사용한다. AI가 원본에 없는 이름, 연락처, 물품, 금액, 시간, 장소 또는 사건 정황을 추정해 추가하지 않는다.
- 일본어 값은 구조화된 원본 필드와 연결한다. 원본 필드가 수정되면 기존 번역을 그대로 재사용하지 않고 해당 필드와 영향을 받는 경위 문단을 다시 생성하거나 무효화한다.
- 이름은 원문과 일본어 표기를 함께 표시할 수 있다. 읽는 법이 확인되지 않은 이름을 임의의 가나 표기로 확정하지 않고 사용자 확인을 요청한다.
- 전화번호, 날짜·시간, 금액과 카드 수량은 표시용 formatter를 사용한다. 저장된 원본 값은 화면용 일본어 문자열로 덮어쓰지 않는다.
- 피해 물품은 안정적인 `id`를 key로 사용하고 사건 카드의 순서를 유지한다. 값이 없는 브랜드·금액·발급사 정보는 문구를 추정하지 않고 해당 세부 줄을 생략하거나 `未確認`으로 명시한다.
- 사건 경위 문단은 확정된 당시 상황을 일본 경찰이 읽을 수 있는 서술형 일본어로 변환하되, 사실의 순서와 의미를 바꾸거나 범죄 유형을 단정하지 않는다.
- 긴 주소, 물품 설명과 경위 문단은 카드 너비 안에서 줄바꿈한다. action 버튼이나 화면 바깥으로 밀어내지 않는다.

## 한국어 확인 모드

- 토글이 꺼져 있으면 제출용 일본어 초안을 표시한다.
- 토글을 켜면 같은 초안의 의미를 검토할 수 있도록 문서 카드의 label과 값을 한국어로 전환한다. 상단 헤더, 안내 카드, 토글과 action 버튼은 원래의 한국어 UI를 유지한다.
- 한국어 확인 내용은 별도의 사건 데이터를 생성하지 않고 일본어 초안과 같은 필드 ID를 사용한다. 두 언어에서 섹션·물품 순서와 누락 여부가 같아야 한다.
- 한국어 확인 모드는 읽기용이며 일본어 원본을 덮어쓰지 않는다. `저장/공유`의 기본 대상은 제출용 일본어 초안이다.
- 번역 전환 중에는 문서 카드에 loading을 표시하고 토글의 연속 입력을 막는다. 실패하면 현재 언어의 내용을 유지하고 토글 가까이에 재시도 안내를 표시한다.

## 저장·공유 및 보안 정책

- `저장/공유`가 하나의 버튼이므로 누른 뒤 저장과 공유 중 선택하는 방식인지, 기기 공유 UI 하나로 두 기능을 제공하는지 구현 전에 확정한다.
- 저장·공유 대상은 기본적으로 일본어 제출용 초안이다. 한국어 확인본을 함께 제공할 경우 파일명과 문서 안에 `확인용 번역`임을 명시한다.
- 파일 형식, 저장 위치, 파일명, 유효 기간, 오프라인 지원과 공유 취소 시 처리를 확정한다. 정책이 확정되기 전에는 실제 저장 완료를 약속하는 UI를 만들지 않는다.
- 이름, 전화번호, 사건 장소, 카드 발급사 등 개인정보를 analytics, 일반 로그, 오류 메시지 또는 파일 URL에 원문으로 남기지 않는다.
- 생성 파일은 인증된 현재 사건에서만 만들고, 만료되거나 권한이 없는 링크로 다른 사용자가 접근할 수 없도록 한다.
- 제출 전 사용자 확인이 필요하며 `AI 신고서 초안 완성`을 경찰 접수 또는 법적 제출 완료로 해석하게 하는 성공 문구를 표시하지 않는다.

- 저장·공유 파일 형식과 일본어 글꼴 포함 방식
- 초안과 생성 파일의 보관 기간, 삭제, 재다운로드 및 접근 권한
- 하단 `Incident` 탭의 실제 목적 route와 한글·영문 탭 label 통일 정책

# S11. 행동 가이드

## 정의 상태

- 이 절은 제공된 S11 와이어프레임의 정보 계층과 서비스 흐름을 기준으로 한 UI·데이터 구조 명세다. 카드 제목, 시간, 순서와 개수는 와이어프레임의 예시이며 고정 문구가 아니다.
- S11은 사용자의 음성 입력과 AI 꼬리질문으로 확정된 사건 카드에 맞춰, 다음에 해야 할 행동을 우선순위 순으로 보여주는 화면이다.
- 가이드 원문과 행동 규칙의 기준은 백엔드 가이드 DB다. AI는 사건 카드의 구조화된 사실과 DB 가이드 후보를 바탕으로 관련 가이드를 선택·정렬·개인화 설명할 수 있지만, DB에 없는 행동 지침을 임의로 만들어 표시하지 않는다.
- S11 route, Screen 뼈대, 앱·웹 View props와 service interface는 생성되었다. 가이드 카드 UI와 mock/API 연동은 아직 구현하지 않는다.

## 가이드 생성·선정 원칙

```text
음성 입력 → AI 꼬리질문 → 확정 사건 카드
                         ↓
             백엔드: 사건 속성으로 가이드 DB 후보 조회
                         ↓
             정책·안전 규칙 필터링 및 우선순위 계산
                         ↓
     AI: 허용된 후보 안에서 맥락 설명·세부 순서 보완
                         ↓
          백엔드 검증 후 S11에 guideId 기반 카드 전달
```

- 사건 카드는 가이드 선정의 단일 입력 기준이다. 사건 유형, 분실·도난 여부, 물품 종류, 현재 위치, 신고 완료 여부, 위험도, 사용자 답변 등 확정된 구조화 필드를 사용한다.
- 백엔드는 사건 카드 조건으로 가이드 DB에서 후보를 조회하고, 국가·지역·기관·시간대·긴급도 같은 하드 규칙을 먼저 적용한다.
- AI가 사용되더라도 반환값은 허용된 `guideId` 목록, 우선순위, 표시 사유와 선택된 행동 파라미터 범위로 제한한다. 가이드 원문·외부 링크·기관 정보는 DB 값만 표시한다.
- 백엔드는 AI 결과의 `guideId`가 후보 목록에 있는지, 현재 사건에 허용되는지 다시 검증한 뒤 클라이언트에 전달한다.
- 긴급 행동은 AI 순위와 무관하게 백엔드 정책의 최상위 우선순위를 가진다. 가이드가 없거나 확신이 낮으면 임의의 안내 대신 안전한 일반 안내와 지원 연결을 표시한다.

## View 계약 — 구현 전

구현 시 앱과 웹은 하나의 `*.types.ts` 계약을 공유한다. 파일 경로와 컴포넌트 이름은 기존 case feature 구조를 확인한 뒤 확정한다.

필수 props 범위는 다음과 같다.

- 현재 사건의 사건번호, 상태, 진행률과 가이드 선정에 사용된 최소 요약 정보
- 가이드 카드 목록: `guideId`, 우선순위, 긴급도, 제목, 설명, 예상 소요 시간, 이미지·아이콘, action 유형과 완료 상태
- 가이드가 현재 사건에 추천된 이유를 위한 짧은 설명과 신뢰·제한 안내
- 조회·새로고침·카드 action·완료 처리·뒤로가기·하단 탭 이벤트
- loading, 빈 목록, 오류, 부분 갱신과 action 처리 상태

## 확정 화면 순서

1. 상단 헤더
   - 좌측 파란 뒤로가기 화살표
   - 중앙 제목 `분실·도난 신고`
   - 우측 단계 표시 `3/6` — 실제 단계 의미는 기획 확인 전
2. 본문 제목
   - 상황에 맞는 행동을 먼저 하도록 유도하는 문구. 와이어프레임의 `지금은 이것부터 해주세요`는 예시다.
3. 현재 사건 요약 카드
   - 사건번호, 신고 상태, 진행률
   - 가이드가 어느 사건을 기준으로 생성되었는지 알 수 있는 최소 정보
4. 우선 행동 가이드 목록
   - 긴급도와 우선순위가 높은 카드부터 표시
   - 각 카드에는 긴급도 badge, 예상 소요 시간, 제목, 짧은 설명, 대표 action과 완료 상태를 표시
   - 카드 우측 보조 아이콘은 순서 변경이 아니라 상세·추가 옵션 또는 상태 확인 용도로만 사용하며, 기능은 구현 전에 확정
5. 기획·정책 안내 영역
   - 가이드 카드의 순서 변경·드래그와 상세 화면 범위를 포함해 확정 전 기능을 안내
6. 하단 내비게이션 `사건`, `가이드`, `서류`
   - `가이드` 활성 상태

## 가이드 카드 규칙

- 카드 내용은 `guideId`를 기준으로 렌더링한다. `분실 카드 즉시 정지`, `가까운 경찰서 확인`, `여권 분실 신고 안내` 등 와이어프레임의 항목을 기본값으로 고정하지 않는다.
- 긴급도는 최소 `긴급`, `중요`, `일반`으로 표현하며 색상만으로 의미를 전달하지 않는다. 각 상태는 텍스트 badge를 함께 표시한다.
- 하나의 카드에는 사용자가 바로 할 수 있는 대표 action을 최대 하나만 우선 노출한다. 예: 전화 연결, 위치 기반 기관 찾기, 상세 안내 보기, 신고서 작성 시작.
- 완료할 수 있는 행동은 완료 상태를 저장하고 목록에서 제거하지 않는다. 완료 시각 또는 `완료됨`을 표시해 사용자가 다음 행동으로 넘어갈 수 있게 한다.
- 순서는 서버가 전달한 `priority`를 사용한다. 클라이언트에서 드래그로 순서를 바꾸더라도 개인 표시 순서만 바꾸며, 안전상 우선 행동의 기본 순위를 낮추지 않는다. 드래그 기능 자체는 기획 확정 전이다.
- 가이드 설명은 확정 사건 카드에서 확인된 사실만 인용한다. 추정이 필요한 경우 단정 대신 확인 행동을 제시한다.

# S12. 인근 기관 안내

## 정의 상태

- 이 절은 제공된 S12 와이어프레임을 기준으로 한 화면·데이터·동작 명세다. 지도 타일, 기관명, 거리, 운영 상태와 주소는 예시이며 실제 서비스에서 고정하지 않는다.
- S12는 사용자의 현재 위치 또는 사용자가 선택한 위치를 기준으로 인근 경찰서, 파출소, 분실물 보관 기관과 대사관을 찾아 길찾기·전화 연결을 돕는 화면이다.
- 현재는 User Flow만 확정한다. `/case/nearby-agencies` route, Screen, 모바일·웹 View, 위치 권한·지도·기관 검색 API와 외부 길찾기 연결은 아직 구현하지 않는다.
- 화면의 목적은 S11 가이드에서 필요한 기관으로 안전하게 이동·연락하도록 돕는 것이다. S14에서 경찰서에 도착한 뒤의 실시간 통역을 대체하지 않는다.

## View 계약 — 구현 전

구현 시 앱과 웹은 하나의 `*.types.ts` View props 계약을 공유한다. View는 지도 SDK, 위치 권한, 전화·외부 지도 실행, route와 기관 조회 비동기 상태를 소유하지 않는다.

필수 props 범위는 다음과 같다.

- 지도 표시 상태: 사용자 위치 좌표 또는 위치 미확인 상태, 현재 선택 기관 좌표, 지도 영역과 지도 제공 불가 fallback
- 선택 기관 카드: `agencyId`, 기관 유형, 이름, 운영 상태, 거리, 예상 이동 시간·수단, 주소, 전화번호, 좌표, 길찾기 가능 여부
- 기관 목록: 기관 유형, 이름, 운영 상태, 거리, 예상 이동 시간·수단, 아이콘, 선택 상태와 상세 진입 가능 여부
- 정렬 기준(`거리순` 기본), 기관 유형 filter, 현재 위치 재조회·지도 레이어 전환 이벤트
- 기관 선택, 길찾기, 전화하기, 전체 목록 보기, 뒤로가기와 하단 탭 이벤트
- 위치 권한, 위치 조회, 지도 로딩, 기관 조회, 길찾기·전화 실행의 loading·오류·빈 목록 상태

권장 도메인 모델은 다음 정보를 포함한다.

```text
NearbyAgency
  agencyId, type(POLICE_STATION | POLICE_BOX | LOST_AND_FOUND | EMBASSY)
  name, address, phoneNumber, latitude, longitude
  operatingStatus(OPEN | CLOSED | UNKNOWN), operatingStatusLabel
  distanceMeters, travelMode(WALK | DRIVE | TRANSIT), travelDurationMinutes
  isNearest, directionsAvailable
```

## 확정 화면 순서

1. 상단 헤더
   - 좌측 뒤로가기 화살표
   - 중앙 제목 `주변 기관 안내`
   - 우측 진행 표시 `3/6`은 제공 와이어프레임 기준이다. 실제 단계 의미는 공통 진행 정책 확정 전까지 고정하지 않는다.
2. 지도 영역
   - 현재 위치는 파란 원형 위치 표시로, 선택 기관은 기관 유형을 구분할 수 있는 marker와 label로 표시한다.
   - 와이어프레임의 시부야역·시부야 경찰서는 예시다. 실제 지도는 사용자의 위치·선택 기관에 맞춰 갱신한다.
   - 우측에는 `현재 위치로 이동`, `지도 레이어 변경` 버튼을 세로로 배치한다. 아이콘만 쓰지 않고 접근성 label을 제공한다.
3. 선택 기관 요약 카드
   - 지도와 목록에서 선택한 기관 하나를 크게 표시한다.
   - `가장 가까운 곳` badge, `운영 중` 같은 운영 상태, 거리와 예상 도보 시간, 기관명, 주소를 표시한다.
   - primary `길찾기`와 secondary `전화하기` 버튼을 제공한다. 전화번호 원문은 버튼에 노출하지 않고 사용자가 action을 실행할 때만 기기 전화 기능으로 전달한다.
4. 주변 기관 리스트
   - 제목 `주변 기관 리스트`와 기본 정렬 `거리순`을 표시한다.
   - 각 행은 기관 유형 아이콘, 기관명, 운영 상태 badge, 거리·이동 수단·예상 시간, 상세 선택 affordance를 포함한다.
   - 예시 순서인 `시부야역 앞 파출소`, `분실물 보관 센터`, `주일 한국 대사관(도쿄)`는 실제 위치·운영 상태·사건 유형에 따라 달라진다.
5. 전체 목록 action
   - `모든 주변 기관 보기`는 map viewport 밖의 기관을 포함한 목록 또는 filter·정렬 화면으로 이동한다. 별도 화면 여부는 구현 전에 확정한다.
6. 하단 내비게이션 `사건`, `가이드`, `서류`
   - 제공 와이어프레임 기준 `가이드` 활성 상태다.

## 기관 표시·정렬 규칙

- 기본 정렬은 거리순이며, 거리 정보가 없으면 목록 끝에 `거리 확인 불가` 상태로 표시한다. 추정 거리를 임의로 만들지 않는다.
- `isNearest`는 현재 선택 기준에서 실제 최단 거리 기관 하나에만 표시한다. `운영 중`은 운영시간 데이터의 기준 시각·시간대가 확인된 경우에만 사용하며, 확인할 수 없으면 `운영 시간 확인 필요`로 표시한다.
- 경찰서·파출소·분실물 보관 기관·대사관은 아이콘과 텍스트 유형을 함께 제공한다. 색상 또는 아이콘만으로 기관 종류나 운영 상태를 구분하지 않는다.
- 사건 유형에 따라 필요한 기관을 우선 노출할 수 있으나, 추천 순서가 거리순을 덮어쓸 때는 `추천` 사유를 함께 표시한다.
- 지도 marker와 목록 행은 같은 `agencyId`를 사용한다. 어느 쪽에서 선택해도 동일한 요약 카드와 선택 상태로 동기화한다.

## 개인정보·안전성·접근성

- 정확한 좌표와 이동 이력은 필요한 조회·길찾기 처리 외에는 화면 상태와 log·analytics·crash message에 장기 저장하지 않는다.
- 위치 권한 거부가 경찰서·대사관 도움 요청을 막지 않도록 수동 위치 선택, 주소 검색 또는 기관 목록 fallback을 제공한다.
- 전화와 외부 길찾기는 앱 밖으로 이동한다는 점을 미리 알리고, 전달 대상은 선택한 기관의 전화번호·좌표·표시명으로 최소화한다.
- 지도 버튼, marker와 목록 행에는 기관명·유형·거리·운영 상태를 포함한 접근성 label을 제공한다. 키보드와 스크린 리더 사용자는 지도 없이도 목록에서 같은 action을 수행할 수 있어야 한다.
- 긴 기관명·주소는 줄바꿈하고 거리·시간·길찾기·전화하기 action이 잘리지 않도록 한다. 모바일·웹은 최대 약 `480px` 콘텐츠 폭과 같은 세로 정보 순서를 유지한다.

## 구현 전 확인할 정책

- 지도 provider, 일본 내 지도·길찾기·대중교통 데이터의 정확도와 사용 비용
- 위치 정확도·갱신 주기, background 위치 사용 여부와 권한 거부 fallback
- 기관 데이터의 출처, 운영 시간·전화번호 검수 주체와 갱신 주기
- 대사관·분실물 보관 기관을 사건 유형·국적에 따라 추천하는 서버 규칙
- 외부 지도·전화 앱이 없는 웹·기기에서 주소 복사 또는 웹 길찾기로 대체하는 방식
- 다국어 기관명·주소·운영 상태의 표시 정책과 긴급 연락처 우선순위

# S14. 경찰서 실시간 대응

## 정의 상태

- 이 절의 화면 구성과 고정 문구는 제공된 S14 와이어프레임과 추가 기획 요구를 기준으로 한다.
- S14는 여행자가 경찰서에 도착한 뒤 S11 행동 가이드를 실제로 수행하도록 돕는 현장 지원 화면이다. S11이 `무엇을 해야 하는지`를 안내한다면 S14는 경찰관에게 사건을 설명하고, 대화하고, 신고서를 작성하는 과정을 실행한다.
- 핵심 흐름은 `사건 설명 → 양방향 통역 소통 → 신고서 초안 확인·작성`의 3단계다.
- 상단에는 확정 사건 카드의 핵심 내용으로 만든 일본어 설명 스크립트를 제공한다. 중단에는 여행자와 경찰관의 발화를 한국어·일본어로 함께 표시한다. 하단에는 Agora 기반 실시간 통역과 S09 신고서 초안 진입을 제공한다.
- 와이어프레임에는 없지만 마이크 버튼 위에 `신고서 초안 생성` CTA를 추가한다. 이미 초안이 있으면 `신고서 초안 보기`로 표시하고 S09로 이동한다.
- 모바일·웹 공통 View, mock interpreter, turn reducer, Screen 수명주기, S14 route와 S11·S09·S07 연결, Agora native RTC adapter·development build 설정까지 구현했다. 마이크 시작 전 여행자 음성 처리 안내와 경찰관 고지 확인을 필수로 받고, 원문 오류를 대화 상태에 보관하지 않는다. 화자·마이크·final 번역 완료 상태의 접근성 안내와 최대 480px 웹 레이아웃도 적용했다. S14 reducer의 언어 방향·이벤트 순서·오류 메시지 비보존은 자동 테스트로 검증한다. 백엔드 STT·번역 transport와 session API가 없으므로 Screen은 아직 mock engine을 사용한다. 실제 백엔드 연결과 Android·iOS 실기기 QA는 아직 완료하지 않는다.
- S14는 전문 통역, 법률 자문 또는 경찰 접수를 대체하지 않는다. 번역 결과와 신고서 초안은 사용자가 원문과 함께 확인할 수 있어야 한다.

## S11 가이드와의 관계

- S11은 사건 카드와 가이드 DB를 기준으로 `경찰서에서 신고하기`, `경찰관에게 사건 설명하기` 같은 현장 행동을 추천한다.
- 사용자가 해당 가이드 카드의 primary action을 실행하면 현재 활성 사건을 유지한 채 S14로 진입한다.
- S14는 가이드의 상세 설명 화면이 아니라 현장에서 가이드를 수행하는 도구다. 설명·통역·신고서 작성 기능을 한 흐름 안에서 제공한다.
- S14를 사용했다고 가이드가 자동 완료되지는 않는다. 사용자가 종료하거나 신고서 단계로 이동할 때 완료 여부를 확인하고 S11의 완료 상태를 갱신한다.

## View 계약

앱과 웹은 `apps/mobile/src/features/police-support/views/PoliceSupportView.types.ts`의 `PoliceSupportViewProps` 계약을 공유한다. View는 표시 값과 사용자 이벤트만 받고 통역 엔진, 권한, route와 비동기 수명주기는 소유하지 않는다.

필수 props 범위는 다음과 같다.

- 사건 카드 기반 일본어 설명 스크립트와 한국어 확인문
- 큰 글씨 모드 여부와 전환 이벤트
- 통역 세션 상태, 현재 발화자 역할과 입력·출력 언어
- 원문·번역문·화자·확정 여부·순서를 포함한 대화 메시지 목록
- 마이크 권한, 녹음·전사·번역·연결 상태와 시작·중지 이벤트
- AI 보조 제안 목록과 제안 실행 이벤트
- S09 초안 존재 여부, 생성 중 여부와 생성·보기 이벤트
- 뒤로가기, S11 복귀와 하단 탭 이벤트
- Agora 연결·전사·번역·권한·네트워크 오류

## 사용자 흐름

```text
S11 현장 가이드 action
        ↓
S14 사건 설명: 경찰관에게 사건 카드 요약 스크립트 제시
        ↓
S14 양방향 소통: 여행자 한국어 ↔ 경찰관 일본어 실시간 통역
        ↓
신고서 작성이 필요한 경우 `신고서 초안 생성`
        ↓
S09 일본어 被害届 초안 확인·수정·저장/공유
```

- 설명 스크립트만으로 접수가 진행되면 통역이나 신고서 단계를 강제로 거치지 않아도 된다.
- 경찰관의 추가 질문이 있으면 양방향 통역을 시작한다.
- 실제 신고서 작성이 필요하다는 안내를 받은 경우에만 S09로 이어질 수 있지만, 사용자가 필요할 때 직접 진입할 수 있도록 CTA는 항상 발견 가능하게 둔다.

   - 와이어프레임 기준 `사건` 활성 상태

## 1단계: 사건 설명 스크립트

- 스크립트는 S05에서 사용자가 최종 확인한 활성 사건 카드의 사건 유형, 주요 피해 물품, 발생 시각·장소와 경찰서 방문 목적만 사용한다.
- 일본어 스크립트와 한국어 확인문은 같은 구조화 필드 ID에 연결한다. 어느 한쪽에만 새로운 사실이 추가되어서는 안 된다.
- 경찰관에게 바로 보여주는 문장은 짧고 단정하게 구성하되, 확인되지 않은 범죄 유형·가해자·정확한 시각·금액을 추정하지 않는다.
- `큰 글씨`는 일본어 제시문을 경찰관이 읽기 쉬운 전체 화면 또는 확대 상태로 전환한다. 한국어 확인문과 앱 조작 요소는 필요할 때 복귀할 수 있어야 한다.
- 사건 카드가 변경되면 기존 스크립트를 그대로 사용하지 않고 다시 생성하거나 무효화한다.
- 스크립트 생성 실패 시 원본 사건 카드의 확인된 필드를 일본어 label과 함께 구조적으로 보여주는 fallback을 제공한다.

## 2단계: Agora 양방향 통역

- 기본안은 경찰서 현장에서 하나의 기기를 여행자와 경찰관이 번갈아 사용하는 turn-taking 방식이다. 상대방이 별도 앱이나 계정을 설치하는 원격 통화 흐름으로 가정하지 않는다.
- 여행자 차례에는 `한국어 → 일본어`, 경찰관 차례에는 `일본어 → 한국어`를 적용한다. 녹음 시작 전에 현재 화자와 원문 언어를 명확히 표시하고 사용자가 전환할 수 있게 한다.
- 중앙 마이크를 누르면 선택된 화자의 발화를 수집하고, 다시 누르거나 무음이 확정되면 해당 발화를 종료한다. 동시에 두 사람의 음성을 한 문장으로 처리하지 않는다.
- 대화 말풍선은 원문과 번역문을 항상 함께 유지한다. 전사 중간 결과는 임시 상태로 표시하고 최종 결과가 오면 같은 메시지를 갱신하며 중복 말풍선을 만들지 않는다.
- Agora RTC 음성 채널과 Real-Time Speech-to-Text·Translation 기능을 조합하는 것을 기본 기술 방향으로 한다. 클라이언트는 백엔드가 발급한 짧은 수명의 토큰과 세션 식별자로 채널에 참여하고, 전사·번역 작업의 시작과 종료는 백엔드가 통제한다.
- 한 기기를 공유하므로 화자 역할을 Agora UID만으로 추정하지 않는다. 앱에서 선택한 발화 차례와 내부 turn ID에 여행자·경찰관 역할을 기록하고, Agora 응답의 메시지 식별자·순서·확정 상태를 함께 사용한다.
- 늦게 도착한 부분 결과가 이미 표시한 확정 원문이나 번역문을 덮어쓰지 않게 한다.
- 1차 범위는 와이어프레임과 같은 실시간 원문·번역 텍스트 표시다. 번역된 음성을 재생하는 speech-to-speech 또는 TTS는 별도 기능으로 보고 자동 재생하지 않는다.
- 통역 중 확인된 새로운 사실은 대화 기록에만 남긴다. 사건 카드 또는 S09 초안에 자동 반영하지 않으며, 사용자가 `사건 정보에 추가`를 명시적으로 확인한 경우에만 구조화한다.
- 한국어↔일본어 언어 조합, 모바일 SDK 지원 범위, 지연 시간, 동시 세션 수, 사용량 비용과 서비스 상태는 구현 전에 실제 Agora 프로젝트 환경에서 검증한다.

## 3단계: S09 신고서 초안 연결

- `신고서 초안 생성`은 현재 활성 사건의 확정 사건 카드를 기준으로 S09 초안을 생성하고 S09로 이동한다.
- 실시간 대화 전체를 그대로 신고서에 삽입하지 않는다. 대화에서 새 사실을 추가하려면 원문·번역문과 함께 사용자 확인을 거쳐 사건 카드에 반영한 뒤 초안을 생성한다.
- 필수 정보가 부족하면 S14에서 임의로 채우지 않고 부족한 항목을 알려 `사건 정보 보완` 또는 기존 확인 화면으로 연결한다.
- 이미 같은 사건의 유효한 초안이 있으면 새로 생성하지 않고 `신고서 초안 보기`로 S09를 연다.
- 사건 카드가 초안 생성 뒤 변경되면 S09의 기존 초안을 `정보 변경됨` 상태로 표시하고 재생성 여부를 사용자에게 확인한다.
- S09 이동 전 통역 세션과 마이크를 안전하게 중지한다. 미확정 발화가 있으면 폐기 또는 확정 여부를 사용자에게 확인한다.

## AI 보조 제안 규칙

- 제안은 가이드 DB와 활성 사건 카드의 확인된 사실을 근거로 한다. 대화 내용은 사용자가 확정한 항목만 의사결정에 사용한다.
- `분실물 목록 보여주기`, `여권 분실 사실 알리기`, `신고서 초안 열기`처럼 현재 화면에서 바로 수행 가능한 행동을 우선한다.
- 법적 결론, 범죄 성립 여부, 경찰의 처리 결과 또는 대사관의 의무를 단정하지 않는다.
- 긴급하거나 안전에 관련된 안내는 일반 AI 제안과 다른 우선순위와 표현을 사용하며, 가이드 DB의 검수된 문구만 표시한다.
- 제안을 눌렀을 때 실행할 대상이 없으면 CTA처럼 표시하지 않고 정보 안내로만 보여준다.

## 음성·번역·개인정보 보호 원칙

- 마이크를 켜기 전에 주변 대화가 수집될 수 있음을 여행자에게 안내하고, 경찰관의 음성을 처리하는 데 필요한 고지·동의 방식을 운영 정책으로 확정한다.
- 기본적으로 원본 음성을 장기 저장하지 않는다. 품질 개선, 분쟁 대응 또는 신고 증빙을 위한 녹음은 별도의 명시적 동의와 보관 정책 없이는 활성화하지 않는다.
- 대화 원문과 번역문에는 여권, 연락처, 주소와 사건 정보가 포함될 수 있다. analytics, 일반 로그와 오류 메시지에 원문을 남기지 않는다.
- Agora App Certificate, REST 자격 증명과 토큰 발급 비밀은 앱에 포함하지 않는다. 토큰은 인증된 백엔드에서 사건·세션별로 짧게 발급한다.
- 채널명과 사용자 UID에 이름, 사건번호, 전화번호 같은 개인정보를 직접 사용하지 않는다.
- 통역 세션 종료 시 마이크 publish, 전사·번역 작업과 채널 연결을 모두 종료한다. 앱 종료나 네트워크 단절에서도 서버 작업이 남지 않도록 만료와 정리 정책을 둔다.
- 번역은 오류가 발생할 수 있으므로 원문을 항상 함께 표시하고, 이름·금액·날짜·여권번호 같은 핵심 정보는 경찰관과 다시 확인하도록 안내한다.
- 긴급 상황에서는 번역 실패가 도움 요청을 막지 않도록 일본 긴급 전화, 직원 도움 요청과 검수된 고정 문구 같은 fallback을 제공한다.

# S19. 이전 사건 정보 입력

## 정의 상태

- 이 절은 제공된 S19 화면을 기준으로 한 UI·기능 명세다.
- S19는 사건번호와 신고 시 설정한 8자 이상 비밀번호로 이전 사건을 불러오는 화면이다.
- 현재는 문서만 확정하며 route, Screen, 모바일·웹 View와 조회 service는 생성하지 않는다.
- 조회 성공 후에는 조회된 사건을 활성 사건으로 설정하고 S07 서류 허브로 이동한다. S20은 S07의 사건카드 `보기`에서 진입한다.

## View 계약 — 구현 전

구현 시 앱과 웹이 하나의 `*.types.ts` 계약을 공유한다. 파일 경로와 컴포넌트 이름은 기존 case feature 구조를 확인한 뒤 확정한다.

필수 props 범위는 다음과 같다.

- 사건번호 값과 변경 이벤트
- 8자 이상 비밀번호 값, 표시 여부와 변경·표시 전환 이벤트
- 제출 가능 여부, 조회 중 여부와 조회 이벤트
- 필드 오류 또는 조회 오류
- 뒤로가기와 `새로운 사건 시작하기` 이벤트
- 하단 탭 선택 값과 탭 이벤트

## 확정 화면 순서

1. 상단 헤더
   - 좌측 파란 뒤로가기 화살표
   - 중앙 제목 `분실·도난 신고`
   - 우측 파란 단계 표시 `3/6`
2. 본문 제목 `이전 사건을 불러올게요`
3. 설명 `분실 또는 도난 신고 접수 시 발급받은 사건번호를 입력해주세요.`
4. 사건번호 입력
   - label `사건번호 입력`
   - placeholder `예: 2024-JP-12345`
5. 비밀번호 입력
   - label `비밀번호 입력`
   - placeholder `신고 시 설정한 비밀번호`
   - 우측 비밀번호 표시·숨김 아이콘
6. 전체 너비 primary CTA `사건 불러오기`

   - 경고 아이콘
   - `사건번호와 비밀번호를 잃어버린 경우 기존 사건을 복구하기 어려워요. 보안을 위해 별도의 찾기 기능을 제공하지 않습니다.`
9. 흰색 데이터 정책 카드

11. 하단 내비게이션 `사건`, `가이드`, `서류`
    - 제공 화면에서는 `서류` 활성 상태

## 입력·검증 규칙

- 사건번호와 비밀번호는 Screen의 로컬 입력 상태로 관리하고 View에는 값과 이벤트만 전달한다.
- 사건번호 앞뒤 공백은 제출 전에 제거한다. 대소문자·하이픈 허용 형식은 백엔드 사건번호 규칙이 확정된 뒤 하나의 validator로 통일한다.
- 비밀번호는 8자 이상 72자 이하로 허용하며 기본 상태에서는 가려서 표시한다.
- 눈 아이콘은 비밀번호의 표시 여부만 전환하며 입력값을 변경하지 않는다.
- 두 값이 모두 유효할 때만 `사건 불러오기`를 활성화한다.
- 조회 중에는 버튼에 처리 상태를 표시하고 입력 변경과 중복 제출을 막는다.
- 인증 실패 메시지는 사건번호의 존재 여부를 노출하지 않도록 `사건번호 또는 비밀번호를 확인해주세요.`처럼 하나의 문구로 처리한다.

# S20. 이전 사건카드 조회

## 정의 상태

- 이 절은 제공된 S20 화면을 기준으로 한 UI·데이터 구조 명세다. 사건 제목, 사건번호, AI 요약, 피해 물품, 현장 단서와 특이사항은 모두 예시이며 고정 문구가 아니다.
- S20은 S19에서 인증해 불러온 이전 사건의 확정 사건카드를 확인하는 읽기 전용 상세 화면이다. 사건 내용을 이 화면에서 다시 편집하지 않는다.
- 기본 진입 흐름은 `S19 이전 사건 조회 성공 → S07 서류 허브 → 사건 카드 (최종) 보기 → S20`이다.
- 새로 작성 중인 사건의 사건카드 상세는 S08이 담당한다. S07은 활성 사건의 출처에 따라 S08 또는 S20으로 연결한다.
- 제공 이미지에 있는 `경찰에게 보여주기(번역)`, `PDF로 저장하기`는 확정 기능이 아니다. 버튼을 기본 기능으로 구현하거나 제공한다고 약속하지 않는다.
- 현재는 문서만 확정하며 S20 route, Screen, View, 상세 조회 service와 내보내기 기능은 생성하지 않는다.

## View 계약 — 구현 전

구현 시 앱과 웹은 하나의 `*.types.ts` 계약을 공유한다. 파일 경로와 컴포넌트 이름은 기존 case feature 구조를 확인한 뒤 확정한다.

필수 props 범위는 다음과 같다.

- 사건번호, 신고 상태, 사건 제목과 발생 유형·일시·장소 등 확정 사건카드 데이터
- 장소 좌표·표시 주소·지도 미리보기 상태. 좌표가 없을 때의 대체 표시도 포함
- AI 사건 요약과 요약의 생성·검토 상태
- 피해 물품 목록과 항목별 상태, 현장 단서·특이사항의 존재 여부
- 뒤로가기, 지도 보기, 후속 action, 하단 탭 이벤트
- 조회 중, 오류, 빈 섹션, 지도 로딩과 후속 action 처리 상태

## 확정 화면 순서

1. 상단 헤더
   - 좌측 파란 뒤로가기 화살표
   - 중앙 제목은 사건카드 상세를 뜻하는 문구. 와이어프레임의 `사건카드 상세`는 예시다.
   - 우측 추가 메뉴 아이콘은 존재할 수 있으나, 메뉴 항목은 구현 전에 확정한다.
2. 사건 식별 정보
   - 사건번호, 신고 상태 badge
   - 사건 제목 또는 사건을 식별할 수 있는 짧은 요약
3. 사건 기본 정보 카드
   - 사건 유형, 발생 일시, 발생 장소
   - 각 정보에는 텍스트 label과 값, 의미를 보조하는 아이콘을 함께 표시
   - 장소 좌표가 있을 때만 지도 미리보기를 표시하며, 지도는 사건카드의 보조 정보다.
4. AI 사건 요약 카드
   - 확정 사건카드의 사실을 읽기 쉬운 문장으로 요약
   - 이미지의 긴 서술은 예시이며, 요약 범위와 문체는 공통 정책으로 결정
5. 피해 물품 목록
   - 물품명, 식별에 필요한 보조 설명, 현재 처리 상태를 항목별로 표시
   - 물품이 없는 사건에서는 임의의 예시 항목을 채우지 않고 빈 상태를 표시
6. 보조 정보 카드
   - 현장 단서, 특이사항처럼 사건에 있을 때만 의미가 있는 정보를 조건부로 표시
   - 긴 내용은 요약 후 `더 보기`로 확장할 수 있으며, 상세 범위는 구현 전에 확정한다.
7. 후속 action 영역
   - 경찰 제시용 번역, PDF 저장, 공유·다운로드 등은 정책·보안·파일 형식이 확정된 경우에만 표시한다.
   - 미확정 상태에서는 이미지와 같은 CTA를 노출하지 않거나, 기능 약속이 아닌 기획 안내로만 표시한다.
8. 하단 내비게이션 `사건`, `가이드`, `서류`
   - `서류` 활성 상태

## 데이터 표시·AI 요약 규칙

- S20은 저장된 사건의 확정 스냅샷을 기준으로 표시한다. 조회 중인 사건의 원본 데이터와 서로 다른 형식·값을 만들어내지 않는다.
- 사건번호 표기는 S06·S07과 같은 formatter를 사용한다.
- 사건 유형, 일시, 장소, 물품 상태는 서버가 저장한 구조화 필드를 우선한다. 값이 없으면 해당 필드를 숨기거나 `확인되지 않음`으로 명시한다.
- AI 요약은 확정 사건카드에 있는 사실만 재서술한다. 원본에 없는 인물·물품·시간·장소·추정을 새로 추가하지 않는다.
- AI 요약은 생성 시점과 사용 모델보다 사건 정보의 정확성을 우선한다. 원본 사건카드가 갱신되면 요약도 재생성 또는 무효화 정책을 따른다.
- 지도 미리보기는 정확한 주소나 좌표가 포함될 수 있으므로, 표시·공유·내보내기 시 위치 정보 공개 범위를 별도 정책으로 따른다.

- S19 헤더에는 별도 조회 흐름의 단계 표시 `3/6`이 있다.
- 앱과 웹이 동일한 `*.types.ts` props를 사용한다.
- 앱과 웹에서 primary·secondary·outline CTA 우선순위가 같다.
- 대기·처리·오류·빈 값·완료 상태가 모두 존재한다.
- 웹의 키보드 Tab 이동과 focus 표시가 가능하다.
- `prefers-reduced-motion`에서 S02 리플 반복을 중지한다.
- 모바일 폭에서 앱 실기기 화면과 같은 순서·간격·줄바꿈을 유지한다.
- 데스크톱에서도 콘텐츠만 중앙 정렬하고 별도의 데스크톱 정보 구조로 바꾸지 않는다.
- S07의 카드 순서, 진행률, 상태 badge와 하단 탭 구성을 모바일과 동일하게 유지한다.
- S19의 입력 순서, 보안 경고, 데이터 정책 카드와 상태별 오류 처리를 모바일과 동일하게 유지한다.
- S11은 서버가 전달한 가이드 우선순위, 긴급도와 action 유형을 모바일·웹에서 동일하게 표시한다.
- S20은 저장된 사건카드의 읽기 전용 정보 구조와, 미확정 내보내기 기능의 비노출 원칙을 모바일·웹에서 동일하게 유지한다.
